## Overview

Hive UK heating thermostats are controlled via the AlertMe Omnia REST API, authenticated through AWS Cognito. The Hive app uses:

- **Auth flow**: `USER_SRP_AUTH` → `PASSWORD_VERIFIER` → `SMS_MFA` (Secure Remote Password + SMS two-factor)
- **Token refresh**: `REFRESH_TOKEN_AUTH` + `DEVICE_KEY` — requires a confirmed and remembered Cognito device
- **API endpoint**: `https://api-prod.bgchprod.info/omnia/`

The challenge this integration solves is running indefinitely in Home Assistant without repeatedly asking the user for SMS MFA codes. This is achieved by confirming a device during the initial setup flow, after which the refresh token + device key combination works for months without MFA.

---

## Architecture

```
config_flow.py          — UI: email/password form → MFA form → entry created
__init__.py             — Integration setup, periodic token refresh (every 45 min)
hive_api.py             — All Cognito auth, token refresh, and Hive API calls
const.py                — Pool IDs, API constants, config key names
```

All blocking operations (boto3, requests) run via `loop.run_in_executor()` to avoid blocking Home Assistant's asyncio event loop.

## Authentication Flow

### Step 1: USER_SRP_AUTH → InitiateAuth

```
POST https://cognito-idp.eu-west-1.amazonaws.com/
X-Amz-Target: AWSCognitoIdentityProviderService.InitiateAuth

{
  "AuthFlow": "USER_SRP_AUTH",
  "ClientId": "3rl4i0ajrmtdm8sbre54p9dvd9",
  "AuthParameters": {
    "USERNAME": "user@example.com",
    "SRP_A": "<2048-bit hex public key>"
  },
  "ClientMetadata": {}
}
```

**Important**: `ClientMetadata: {}` must be sent even though it is an empty object. Hive's Cognito pool has a Lambda Pre-Authentication trigger that gates device tracking on this field being present. If omitted, Cognito still authenticates the user but does not create the pending device record needed for `ConfirmDevice` later.

The SRP_A value is generated by `pycognito.aws_srp.AWSSRP.get_auth_params()`. It is a large random 2048-bit number (`a`) exponentiated mod the standard SRP group prime N: `A = g^a mod N`.

**Response**: `ChallengeName: PASSWORD_VERIFIER` plus `ChallengeParameters` containing the server's SRP values.

### Step 2: PASSWORD_VERIFIER challenge

```
POST https://cognito-idp.eu-west-1.amazonaws.com/
X-Amz-Target: AWSCognitoIdentityProviderService.RespondToAuthChallenge

{
  "ClientId": "3rl4i0ajrmtdm8sbre54p9dvd9",
  "ChallengeName": "PASSWORD_VERIFIER",
  "ChallengeResponses": {
    "USERNAME": "906f886f-fa3d-418c-b2ca-289edf5ed1fb",   ← UUID, not email
    "PASSWORD_CLAIM_SECRET_BLOCK": "<base64 server blob>",
    "PASSWORD_CLAIM_SIGNATURE": "<base64 HMAC-SHA256 signature>",
    "TIMESTAMP": "Mon Mar 30 19:12:07 UTC 2026"
  }
}
```

The `USERNAME` here is the Cognito internal UUID (`cognito:username`), not the user's email address. Cognito resolves the email to UUID in Step 1 and returns the UUID in `ChallengeParameters["USERNAME"]`. `pycognito.aws_srp.AWSSRP.process_challenge()` handles this automatically — it reads the UUID from `ChallengeParameters` and puts it in the response.

The signature is an HMAC-SHA256 of: `pool_name || UUID || secret_block || timestamp`, keyed with a Hkdf-derived key from the SRP shared secret `S = B^(a + u*x) mod N`.

**Response**: `ChallengeName: SMS_MFA` plus a `Session` token.

### Step 3: SMS_MFA challenge

```
POST https://cognito-idp.eu-west-1.amazonaws.com/
X-Amz-Target: AWSCognitoIdentityProviderService.RespondToAuthChallenge

{
  "ClientId": "3rl4i0ajrmtdm8sbre54p9dvd9",
  "ChallengeName": "SMS_MFA",
  "Session": "<session token from step 2>",
  "ChallengeResponses": {
    "SMS_MFA_CODE": "123456",
    "USERNAME": "906f886f-fa3d-418c-b2ca-289edf5ed1fb"   ← UUID, not email
  }
}
```

**Critical**: `USERNAME` must be the UUID here too, not the email. Using the email causes Cognito to authenticate the user successfully but does NOT create the pending device record in the device tracking table. `ConfirmDevice` then fails with `InvalidParameterException: Invalid device key given` because there is nothing to confirm.

The UUID is saved from Step 2's `challenge_responses["USERNAME"]` (which `process_challenge()` populated) into `_mfa_challenge["_srp_username"]` before the `SMSMFAChallengeException` is raised. When the user enters their MFA code in the HA UI and the flow resumes, this UUID is read back and used in the `ChallengeResponses`.

**Response**: `AuthenticationResult` containing `AccessToken`, `IdToken`, `RefreshToken`, plus `NewDeviceMetadata` containing `DeviceKey` and `DeviceGroupKey`.

### Step 4: ConfirmDevice

Called immediately after Step 3 using the `AccessToken` and `DeviceKey` from `NewDeviceMetadata`.

```
POST https://cognito-idp.eu-west-1.amazonaws.com/
X-Amz-Target: AWSCognitoIdentityProviderService.ConfirmDevice

{
  "AccessToken": "<access token from step 3>",
  "DeviceKey": "eu-west-1_xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
  "DeviceName": "Home Assistant",
  "DeviceSecretVerifierConfig": {
    "Salt": "<base64-encoded 17-byte big-endian salt>",
    "PasswordVerifier": "<base64-encoded 256-byte big-endian SRP verifier>"
  }
}
```

**Device password**: A fresh 40-byte random value is generated (`os.urandom(40)`) and base64-encoded to produce the `device_password`. This is used as the password in the SRP verifier computation and stored alongside `device_key` and `device_group_key` so that future `REFRESH_TOKEN_AUTH` can use it.

**SRP verifier computation** (`_compute_device_verifier`):

```python
salt_bytes = os.urandom(16)
inner = SHA256(device_group_key + device_key + ":" + device_password)
x_bytes = SHA256(salt_bytes + inner)
x = int.from_bytes(x_bytes, "big")
verifier = pow(g, x, N)   # g=2, N=2048-bit SRP prime
```

Both `salt_bytes` and `verifier` are encoded as **positive big-endian integers** with a `0x00` prefix byte prepended if the high bit is set. This matches Cognito's Java `BigInteger` deserialization which interprets the bytes as a signed two's-complement value. Without the prefix, a salt or verifier whose first byte ≥ 0x80 would be decoded as a negative number, causing a `Found negative value for salt or password verifier` error from Cognito.

**Response**: `{"UserConfirmationNecessary": true}` — this means the pool is configured as "User Opt-In" device tracking (not "Always remember"), so the integration must explicitly call `UpdateDeviceStatus("remembered")`.

### Step 5: UpdateDeviceStatus

```
POST https://cognito-idp.eu-west-1.amazonaws.com/
X-Amz-Target: AWSCognitoIdentityProviderService.UpdateDeviceStatus

{
  "AccessToken": "<access token from step 3>",
  "DeviceKey": "eu-west-1_xxxxxxxx-...",
  "DeviceRememberedStatus": "remembered"
}
```

After this call the device is fully registered. The `REFRESH_TOKEN_AUTH` flow with `DEVICE_KEY` will work with the `RefreshToken` issued in Step 3.

## Token Lifecycle and Refresh

Cognito tokens:

| Token | Lifetime | Used for |
|-------|----------|----------|
| `AccessToken` | 60 minutes | Cognito device API calls (`ConfirmDevice`, `UpdateDeviceStatus`) |
| `IdToken` | 60 minutes | Hive API calls (`Authorization: Bearer {id_token}`) |
| `RefreshToken` | Long-lived (~30 days typical, but varies by pool config) | Obtaining new Access + Id tokens |

The integration refreshes every 45 minutes via `REFRESH_TOKEN_AUTH`:

```
POST https://cognito-idp.eu-west-1.amazonaws.com/
X-Amz-Target: AWSCognitoIdentityProviderService.InitiateAuth

{
  "AuthFlow": "REFRESH_TOKEN_AUTH",
  "ClientId": "3rl4i0ajrmtdm8sbre54p9dvd9",
  "AuthParameters": {
    "REFRESH_TOKEN": "<refresh token>",
    "DEVICE_KEY": "eu-west-1_xxxxxxxx-..."
  }
}
```

`DEVICE_KEY` must be included because Cognito's pool has device tracking enabled. Without it, Cognito may return a `DEVICE_SRP_AUTH` challenge (device password verification), which would require an additional round-trip.

The refresh token itself is **not rotated** by `REFRESH_TOKEN_AUTH` — the same token is reused until it expires or is invalidated (e.g. by a password change or explicit sign-out).

## Device Tracking — Why It Matters

Cognito "User Opt-In" device tracking means:

1. On every successful `USER_SRP_AUTH` + `SMS_MFA`, Cognito issues a new pending `DeviceKey` in `NewDeviceMetadata`.
2. The app must call `ConfirmDevice` (registers the device password verifier) and `UpdateDeviceStatus("remembered")` to mark the device as trusted.
3. Subsequent `REFRESH_TOKEN_AUTH` calls from a trusted device succeed without requiring MFA.
4. If the device is not confirmed/remembered, `REFRESH_TOKEN_AUTH` works for the first refresh but subsequent refreshes may require a `DEVICE_SRP_AUTH` challenge or fail outright.

This is why without device tracking, the integration would need to prompt for SMS MFA every time the access token expires (~1 hour).

## Key Technical Details and Gotchas

### The UUID vs Email Problem

Cognito internally identifies users by a UUID (`cognito:username`), but users sign in with their email address. Cognito resolves email → UUID during `InitiateAuth` and returns the UUID in `ChallengeParameters["USERNAME"]` of the `PASSWORD_VERIFIER` challenge.

The `SMS_MFA` challenge response must use this UUID as `USERNAME`. If the user's email is used instead:

- Cognito authenticates the user successfully (the session token links the challenges together, not the USERNAME field).
- However, the device tracking subsystem does NOT create a pending device record.
- `ConfirmDevice` fails with `InvalidParameterException: Invalid device key given` because there is no pending record to confirm.

This was the root cause of all `ConfirmDevice` failures during development. The fix is to save `challenge_responses["USERNAME"]` (the UUID returned by `process_challenge()`) before raising the `SMSMFAChallengeException`, then use it when responding to the SMS_MFA challenge.

### ClientMetadata in InitiateAuth

Hive's Cognito pool has a Lambda Pre-Authentication trigger that inspects `ClientMetadata`. The Hive iOS app (AWS Amplify v5) always sends `ClientMetadata: {}` in `InitiateAuth`, even though the object is empty.

If `ClientMetadata` is absent entirely:

- Authentication succeeds normally.
- But the Lambda trigger does not run the device-tracking setup path.
- `NewDeviceMetadata` may still appear in the response (Cognito's default behaviour), but the Lambda's internal state needed for device confirmation is absent.

Solution: always send `ClientMetadata: {}` in `InitiateAuth`. This is done via a direct `boto3` call rather than through `pycognito`'s `authenticate()` method, because `pycognito` v2024.5.1 never passes `ClientMetadata` to `initiate_auth()` regardless of the `client_metadata` argument (it uses `if client_metadata:` which treats empty dict as falsy).

### SRP Verifier Encoding

AWS Cognito's Java backend uses `new BigInteger(1, bytes)` to decode the Salt and PasswordVerifier from their base64 representations. `BigInteger(1, ...)` treats the byte array as an unsigned big-endian value regardless of the sign bit.

However, `BigInteger` constructors that do NOT take a signum argument (used in some validation paths) interpret the first bit as a sign bit. To be safe, the integration follows the same convention as the Amplify SDK: prepend a `0x00` byte to both the salt and verifier if the first byte has its high bit set (`>= 0x80`). This ensures the value is always interpreted as positive.

Without this prefix on the salt, a salt whose first byte ≥ 0x80 would produce `Found negative value for salt or password verifier` from Cognito — an error seen during development when `_pad_unsigned` was temporarily removed from the salt encoding path.

### pycognito Limitations

The integration uses `pycognito.aws_srp.AWSSRP` only for the SRP mathematics (`get_auth_params()` and `process_challenge()`). All actual Cognito API calls are made via direct `boto3.client("cognito-idp")` calls. This is because:

1. `pycognito.Cognito.authenticate()` ignores `client_metadata={}` (falsy check bug).
2. `pycognito.Cognito.authenticate()` does not expose intermediate challenge handling needed to interleave MFA with `ConfirmDevice`.
3. Direct boto3 calls give full control over every request body field.

## The Hive API

Base URL: `https://api-prod.bgchprod.info`

Required headers on every request:

```
Authorization: Bearer {id_token}
Content-Type: application/json
Accept: application/vnd.alertme.zoo-6.5.0+json
X-API-Key: 7Y1kj281ay64CAik9YTcnaFNqdiSPksW5XP2GZ4T
X-Omnia-Client: 14.04.2 build 5
User-Agent: Hive/14.04.2 iOS/26.2.1 Apple
```

**API version note**: Version `6.5.0` returns full `heating_thermostat_v1` data including `heatSchedule`. Version `6.6.0` returns empty feature arrays and is not usable.

### Key endpoints

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/omnia/nodes/?homeId={id}` | List all nodes (thermostats, receivers, etc.) |
| GET | `/omnia/nodes/{nodeId}/features/heating_thermostat_v1` | Read current schedule |
| PUT | `/omnia/nodes/{nodeId}/features/heating_thermostat_v1` | Update schedule |

Note: `PUT /omnia/nodes/{nodeId}` returns `405 Method Not Allowed`. Only the feature-specific endpoint accepts schedule writes.

### Schedule data structure

Schedules use Hive's `heatSchedule` format with `setpoints`:

```json
{
  "heatSchedule": {
    "setpoints": [
      {
        "dayIndex": 1,
        "time": 19200,
        "value": 190
      }
    ]
  }
}
```

- `dayIndex`: 1=Monday … 7=Sunday
- `time`: seconds since midnight (e.g. `19200` = 05:20:00)
- `value`: temperature in tenths of a degree Celsius (e.g. `190` = 19.0°C)

## Config Entry Data Structure

After a successful setup flow the config entry `data` dict contains:

| Key | Source | Purpose |
|-----|--------|---------|
| `email` | User input | Username for re-authentication |
| `password` | User input | Password for re-authentication |
| `id_token` | Cognito SMS_MFA response | Hive API bearer token (short-lived) |
| `access_token` | Cognito SMS_MFA response | Cognito device API token (short-lived) |
| `refresh_token` | Cognito SMS_MFA response | Long-lived token for REFRESH_TOKEN_AUTH |
| `user_id` | Decoded from id_token | Cognito `cognito:username` UUID |
| `home_id` | Hive nodes API | AlertMe home identifier |
| `device_key` | Cognito NewDeviceMetadata | Cognito device identifier |
| `device_group_key` | Cognito NewDeviceMetadata | Cognito device group (pool-specific prefix) |
| `device_password` | Generated locally | 40-byte random, base64-encoded; used for device SRP |

After initial setup, `id_token` and `access_token` are refreshed every 45 minutes and written back to the config entry. `refresh_token` and device credentials do not change during normal operation.

## Emergency Override (Options Flow)

The Options flow (accessed via the integration settings in HA) exposes all device credentials and the refresh token as writable fields. Under normal operation these are set automatically and should not be changed.

Use these fields only if:

- Automatic token refresh has stopped working and you cannot remove/re-add the integration (e.g. you need to preserve automations that reference service calls).
- You want to inject credentials extracted from an iOS MMKV backup (using `find_hive_device_creds.py` in this repo) to take over a device session from the iOS app.

**iOS MMKV backup extraction**: The Hive iOS app stores Cognito device credentials in MMKV binary format. If you have an iMazing backup of the Hive app, the MMKV file is at:
```
Documents/mmkv/auth
```
The `find_hive_device_creds.py` script parses the binary format and extracts `deviceKey`, `deviceGroupKey`, and `randomPasswordKey`. These map directly to `device_key`, `device_group_key`, and `device_password` in the Options form.

MMKV binary format: 4-byte LE `actual_size` + 4-byte CRC + varint-prefixed key-value pairs. Each value has an extra varint-length prefix that must be skipped to get the string content.

## HACS Packaging Notes

To publish on HACS:

1. Create a new GitHub repository.
2. Copy the following to the repo root:
   - `hacs.json` (from this repo's root)
   - `README.md`
   - `README_DETAIL.md`
3. Copy `custom_components/hive_schedule_manager/` into `custom_components/hive_schedule_manager/` in the new repo.
4. Generate `icon.png` from `images/icon.svg` using `generate_icon_png.py`.
5. Delete `hacs.json` from inside `custom_components/hive_schedule_manager/` (it is a reference copy only).
6. Create a GitHub release with a semantic version tag (e.g. `v2.0.0`) matching `manifest.json`'s `version` field.
7. Submit to HACS default repository list or install via HACS custom repositories.

**Dependencies** (declared in `manifest.json`, installed automatically by HA):
- `pycognito==2024.5.1` — SRP mathematics (`AWSSRP` class only)
- `requests>=2.31.0` — HTTP calls to the Hive API

`boto3` is available in HA's standard environment and does not need to be declared as a dependency.
